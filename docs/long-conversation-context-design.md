# 长期对话的上下文：到上限就换一条空线程

状态：**v3，Main Bot 部分已实现**（2026-11-17）。角色 bot 还没做。

## 问题

桌面端的 Main Bot 是一条不结束的对话。它每一轮都把完整历史发给模型，靠核心的通用压缩兜底，而那套压缩是为"防止溢出"设计的：

- 触发点是窗口减去 3.3 万 token（`src/context/budget.ts` 的 `shouldTriggerCompact`）。Main Bot 现在用的 Gemini 4 Carbon 窗口是 1,048,576，所以要到约 101 万 token 才压缩。
- 2026-11-17 正式数据里 Main Bot 一共 53 条消息、约 2400 个字符。按这个量，压缩实际上不会发生。

结果是对话越长每一轮越贵越慢，而几个月前某件小事的回报会一直留在上下文里。长期对话需要的是控制规模，不是防溢出。

角色 bot（开发、评审）也是一条持续的对话，有同样的问题，只是来得更快：它们的上下文里是代码和命令输出。

## 参照

Aegis（`~/coworker`）的 `feat/main-bot` 分支已经解决了这个问题，提交 `3e68ecca`"keep the bot's state outside its conversation"。代码在 `src/electron/libs/main-bot/`，测试在 `scripts/tests/main-bot.test.ts`。它的做法是让对话可以随时丢掉：

1. 要记住的东西不放在对话里：笔记是 markdown 文件；派出去的活记在表里（目标、最后一次回报的要点、是否已告知）；现状每轮由应用现查现给。
2. 上下文到上限时，agent 换到一条空线程。用户看到的对话不变，只多一条分隔线。
3. 换完之后重新交底。内容来自记录而不是模型写的摘要：最近 6 轮的节选、最近 5 件活的回报要点、笔记。
4. 指令里明说这段对话留不住，要留下的东西在知道的那一轮就写进笔记。

本设计照这个思路做，数值也沿用它的，除非下面另有说明。

第二个参照是 DS Bot（`Fei2411/DS-Bot`，Apache-2.0），设计在 `docs/plans/2026-10-09-context-and-memory.md`，代码在 `ds-bot/src/host/steward.js` 和 `parts.js`。它的 bot 也是一条长期对话、背后分成若干段，但换段的办法不同：

1. 过线之后先由一个"上下文管家"判断活是不是告一段落。这是一次单独的小请求，只看最近约 6,000 token 的消息，回答"换段"还是"压缩"。
2. 没做完：原地压成检查点，接着干。检查点是模型写的摘要，加上用户和其他 bot 发来的原话。
3. 告一段落：bot 自己写一份交接笔记（目标、约束、进展、决定、要保留的事实、未了的事、下一步、去哪找），新段以"笔记 + 最近消息原文"开头。
4. 旧的段整份留着，bot 有一个 `read_own_chat` 工具能搜全部的段，包括被压缩掉的消息。
5. 过线的位置跟着模型走：可用窗口的 80%，另有 380,000 token 的绝对上限。代码里的理由是前缀缓存在几十万 token 以上就帮不上忙了。
6. 用户完全无感：不显示分隔，也不显示上下文用了多少。这一点本设计不取，见下。

两个方案的差别在于"丢掉对话之后靠什么接上"。Aegis 靠应用记下的结构化记录，不花模型调用；DS Bot 靠模型写的笔记和摘要，外加一个能搜旧对话的工具兜底。本设计取 Aegis 的做法为主，从 DS Bot 取三样，见下面"从 DS Bot 取的"。

## 从 DS Bot 取的

**搜旧对话的工具。** 初稿里，bot 在空线程上找不到用户提到的东西时只能问用户。DS Bot 的 `read_own_chat` 说明有更好的办法：旧线程本来就整份留着，给 bot 一个搜它们的工具，记录没覆盖到的细节可以自己找回来。本设计加上这个工具，问用户退为找不到之后的最后一步。

**"活做没做完"决定怎么处理。** DS Bot 用一次模型调用来判断。Bubble 不需要：一个 bot 手上有没有没交差的工单、有没有问了还没答的问题，应用自己知道。所以规则可以是确定的：没有未了的事，换线程；有，原地压缩（核心已有的压缩），等它做完再换。Main Bot 自己不干活，状态都在工单里，它永远算"没有未了的事"；这条规则是给以后的角色 bot 准备的。

**上限因角色而异。** Aegis 的 100,000 和 DS Bot 的 380,000 差了近四倍，原因是 bot 的性质不同。Main Bot 只做转述和分派，旧对话几乎没有价值，上限低一些只有好处；写代码的 bot 上下文里是读过的文件和试过的办法，丢了要重新读，上限应该高。所以上限做成对话的参数。Main Bot 的绝对上限本稿原想用 100,000，用户定为 500,000，比两个参照都高；角色 bot 那一版再定。

没有取的：界面上无感（用户要分隔线，这样 bot 不记得更早的事时看得出原因）；模型写的交接笔记和检查点。Main Bot 用不上；角色 bot 那一版是否需要，到时候看记录够不够再说。

## 放在哪一层

换线程这件事分成两半：

- **机制**：量上下文、判断该不该换、开新线程、从旧线程里取最近几轮、记住"换过了还没交底"。这些只和会话有关，核心自己都知道。
- **事实**：现在谁在干活、最近的回报说了什么、笔记里有什么。这些是某个应用自己的东西。

机制放进 SDK，事实由宿主应用提供。理由：

1. 核心只有 TS 一套，桌面的 bot 协调逻辑迟早要从 Rust 界面进程搬到 TS 这边（本地和云端都要用）。机制写在 SDK 里以后不用再搬。
2. Aegis 和 Bubble 桌面的 Main Bot 都跑在 Bubble SDK 上。机制进了 SDK，两边用同一份；Aegis 现在那份可以作为移植的蓝本，测试也能跟着移。
3. 飞书宿主（`serve --feishu`）里的长对话有同样的问题，以后可以直接用。

备选是全部写在 Rust 里：事实都在本地，约三百行就够，最快。代价是搬迁时重写一遍，而且 Aegis 那边仍是另一份。不选它。

## 设计

### SDK：长期对话

代码在 `src/sdk/conversation.ts`，从 SDK 导出；`bubble host` 在 `src/host/server.ts` 里用它。

一个长期对话由若干条线程（会话）前后相接组成，同一时刻只有最新一条在用。宿主应用始终用第一条线程的会话 id 称呼它；之后的线程由 SDK 命名为 `<会话 id>.t2`、`.t3`……事件、停止、状态、历史这些按会话 id 的操作，宿主都换算到当前线程上，应用不用知道换过。

回合带上 `conversation` 就是长期对话（协议里是 `turn/start` 的同名参数）：

```ts
conversation?: {
  /** 应用在对话之外留着的东西。每轮都传，轮到交底时才用。 */
  brief?: string;
  /** 现状，应用从自己的记录里现查的。每条消息都带。 */
  standing?: string;
  /** 上下文上限，缺省见"触发规则"。 */
  limit?: { tokens?: number; share?: number; belowCompaction?: number };
  /** false：只在有人要求时换。缺省 true。 */
  automatic?: boolean;
}
```

一轮结束时，宿主拿这一轮最后一次 `context_usage` 判断上下文是不是过了上限，过了就记下"下一轮换"。真正换线程发生在下一轮开始时：开一条新会话（文件夹同第一条），记下"待交底"，并通知应用。这样换线程只会发生在两轮之间，也不需要在空闲时替应用做事。

待交底时，这一轮的消息前面加一段交底；这一轮成功结束才清掉"待交底"，失败的那一轮可能什么都没告诉模型。

发给模型的消息由三部分拼成：`<conversation_brief>`（待交底时才有）、原消息、`<conversation_standing>`。这两个标签是 SDK 自己加的，所以取节选和搜旧对话时能把它们去掉，只留用户原话。

有人要求换时调 `conversation/fresh`：没有回合在跑就立刻换，回答里带上新线程的序号；有回合在跑就记下，下一轮开始时换。

对话的状态（线程列表、换线程后答过几轮、空线程的基线用量、待办标记）存成 `<BUBBLE_HOME>/conversations/<会话 id>.json`。删除会话时每条线程和这个文件一起删。

和初稿不同的两处：

- **交底的事实随回合一起传，而不是宿主回头问应用。** 应用在等 `turn/start` 的回答时还没开始读这一轮的消息，宿主这时问它会互相等住。应用每轮多查几张工单的代价可以忽略。
- **换线程用通知而不是会话事件。** `conversation/fresh { sessionId, trigger, part }` 在回合开始时发出；手动且立刻生效的那次不发通知，由回答告诉应用。

### 触发规则

上限取三者中最小的：

| | 值 | 用意 |
|---|---|---|
| 绝对上限 | 500,000 token | 大窗口模型不必每轮把整个窗口重读一遍 |
| 窗口的比例 | 60% | 小窗口模型留出余地 |
| 核心自动压缩点的比例 | 80% | 在核心自己压缩之前换，丢什么由这里决定。核心按估算值判断，估算偏高，所以留 20% |

对 Gemini 4 Carbon（窗口 1,048,576）是 500,000 token；对窗口 200,000 的模型是 120,000。绝对上限初稿照 Aegis 定的是 100,000，用户定为 500,000。

三条防抖，照搬 Aegis：

- 只在两轮之间换。
- 换完之后至少答过 5 轮，才能再自动换。
- 用量比空线程刚开始时的基线至少多出上限的 25% 才换。否则空线程本身就超线（笔记很多、工具定义很大）时会反复重开。

算出的上限低于 16,000 token 时不自动换，交给核心的压缩。记下"下一轮换"之后，如果核心自己已经把上下文压下来了，就取消。

### 交底

空线程的第一轮，消息前面加一段，由两部分拼成：

1. **SDK 自己取的**：上一条线程最后 6 轮的节选，新的优先，总共不超过 10,000 字符。每轮里发来的话截到 500 字符，回答截到 1,200 字符并保留头尾；最后一次回答放宽到 4,000 字符，因为用户可能正在回它。被截断的引用后面写明完整内容在哪：`(cut short; read_own_chat with around "part 1 #3" shows all of it)`。
2. **宿主给的**：这一轮 `conversation.brief` 的原文，SDK 不解释它的内容。

开头固定一句：上下文从这里重新开始，对话之前一直在进行，用户仍然看得到全部，但你已经没有它了；之前的对话都还存着，用 `read_own_chat` 能搜到；搜不到再问用户，不要猜。

截断处的那句提示是真实模型验证时加的：没有它，模型把截断的引用当成全部，说"我这里没有了，你往上翻"，而不去搜。

### 搜旧对话

长期对话的回合多一个工具 `read_own_chat`，由宿主自己执行，只在这个对话的线程里搜（当前这条和之前的每一条）：

- `query`：按词搜，要求每个词都出现，返回最新的 8 条，每条带锚点（`[part 2 #14]`：第几条线程、其中第几句话），长的截到命中处附近。
- `around`：给一个锚点，看那条消息的全文和前后各两条。

直接扫会话日志，不建索引。Main Bot 的对话量小，够用；慢了再加索引（DS Bot 用的是 SQLite FTS5 加 trigram 分词，中文不用切词）。这里的搜索是子串匹配，中文同样不用切词。

### 桌面：Main Bot

Main Bot 的每一轮都带 `conversation`。应用这边做了四件事。

**交底的事实**（`manager::kept_outside`）：最近 5 张有回报的工单，新的在前，每张一行：给了谁、标题、怎么结束的、多久以前、回报的要点。要点取回报的头尾，不超过 200 字符。末尾一句提示：`list_bots` 和 `get_bot` 能看全部，团队笔记在系统提示里。

**每轮的现状**（`manager::how_things_stand`），现查现给，不依赖对话：

- 等用户的：在等回答或等批准命令的 bot、上一轮失败的 bot、待点头的工单，最多 12 条。
- Main Bot 交出去还在干的：bot 名、工单标题、多久以前给的，最多 12 条。
- 其他在干活的（GitHub、Routine、别的 bot 带来的），最多 8 条。

放在消息末尾而不是系统提示里：系统提示每轮都变会让整条线程的提示缓存失效。

**提示词**（`manager::LASTING`）：每条消息末尾的现状比之前说过的话可靠；这段对话留不住，搜得到；要留下的东西在知道的那一轮就记进团队笔记，什么值得记、什么不值得；用户纠正做法时先记再答。Main Bot 之前没有记忆工具的用法说明，这段一并补上。

**界面**：对话里换线程的位置画一条居中的细线，写 "Context starts afresh here"，自动换和手动换都画；它存成一条 `fresh` 角色的消息，重启后还在原处。手动入口在设置 → Models 的 "Main bot's context" 一行（Main Bot 没有详情面板）。Main Bot 搜旧对话时，状态行显示 "Looking back at what was said"。

### 协议

`bubble host` 的协议加了：`turn/start` 的 `conversation` 参数、请求 `conversation/fresh`、通知 `conversation/fresh`。协议版本从 1 升到 2：应用给旧宿主传 `conversation` 会被不声不响地忽略，版本号让两边对不上时在启动时就报出来；打包脚本也会核对。

## 不做的

- 不写摘要，不设判断"活做没做完"的模型调用。交底只用记录和节选，做没做完看工单。
- 不动核心的通用压缩。没带 `conversation` 的会话行为不变。
- 这一版不给角色 bot 用。它们要用到"有未了的事就原地压缩"那一半，需要 SDK 能把核心压缩的触发点调低（现在固定在窗口减 3.3 万），交底内容也不一样（手上的工单、项目笔记），上限也要另定。等 Main Bot 这边用稳了再做。
- 不做 Aegis 的"每 20 轮重发指令"和"笔记变了才提示"：Bubble 的指令和团队笔记在系统提示里。

## 阶段

1. **SDK 和协议。** 已做。测试在 `src/sdk/__tests__/conversation.test.ts` 和 `src/host/__tests__/server.test.ts`。还没合进 `main`，也没发 npm 版本。
2. **桌面。** 已做。测试在 `native/app/tests/long_conversation.rs`（手动重开、交底内容、分隔线的位置、重启后还在）和 `manager.rs` 的单元测试。
3. **真实模型验证。** 已做（Gemini 4 Carbon）。脚本是 `walkthrough.rs` 里的 `a_fresh_context_with_a_real_model`：先说一段长话，末尾带一件只管这一次的事；再说一条值得记的偏好；手动重开上下文；然后问三件事。结果：只在旧对话里的那件事，它调 `read_own_chat` 找了出来；偏好从笔记里答出；从没说过的事，它搜了两次后说没有并请用户再说一遍，没有编。自动触发（上下文真的长到上限）没有用真实模型跑，靠单元测试覆盖。

## 待定

1. 换线程时要不要先让 Main Bot 跑一轮"把还没记下的东西写进笔记"。Aegis 没有这一步，靠提示词要求它平时就记。真实模型验证里它平时确实会记，而且没记的也搜得回来，所以现在不加。
2. 角色 bot 那一版：上限定多少，交底里放什么，以及"有未了的事就原地压缩"需要 SDK 能调低核心压缩的触发点。
